# 前后端一体化演示路线

目标是做出可以现场演示、结果可核查的 Knowledge CI 工作台：修改知识后，观众能看到版本变化、自动评测结果，以及支持判断的原始证据。本路线以验收结果安排依赖，不承诺未经估算的完成日期。

本轮完成真实项目文档的后端验收和路线规划，没有开发新页面、管理 API、MCP 或部署服务。前端目前仍是 V2 静态演示；后续优先恢复前后端联调，原先的 V3/V4 暂停不再作为长期方向，但尚未执行对应开发。

## 本次验收提供了可演示的事实

2026-11-13 的隔离运行使用现有 `docs/auto-evaluation.md` 和 `docs/acceptance.md`，导入 11 个知识单元。评测集在首次发布后冻结，共 4 条用例，包含多证据与无答案问题。正向变更、故障注入和恢复均通过正式 CLI 导入触发自动评测。故障时 Recall@5 从 1.0 降到 0.666667，恢复后回到 1.0；失败记录保留，重复导入不产生新任务。

这是项目文档的真实验收，覆盖本机 SQLite 与 lexical 检索。它不证明生产业务效果、模型语义理解、生成答案正确性或完整 Agent 任务成功率。本次使用默认绝对质量门禁，没有自动接受基线或宣称已完成 delta 回归。

目前后端已经能提供版本、稳定 lineage、引用证据、时效与冲突信息，以及自动评测任务历史。前端已有总览、溯源与版本 Diff。主要缺口是管理数据尚未暴露为面向工作台的读取 API，评测任务也尚未进入页面。

## 产品特色围绕变更展开

工作台默认从一次知识变更进入，展示该次变更的 revision、关联任务和固定评测集。用户先回答“这次改动是否通过”，再查看相关的知识版本与引用。

- **结果能回到证据**：从评测任务进入版本 Diff，再定位知识单元与原文范围，显示来源、版本及知识状态。
- **失败与修复都有记录**：现场展示一次正常更新、一次质量下降和一次修复。修复新增任务，不覆盖失败报告。
- **知识有时间边界**：并排查看当前有效知识与历史版本，区分 stale、superseded 和退役内容，不让旧知识悄悄替当前版本作答。
- **指标有适用范围**：页面同时显示检索模式、TopK、评测集版本、门槛与知识指纹。引用完整不等于答案正确，相关变化也不自动等于因果归因。

视觉上保留现有 V2 基础，优先建立统一的变更时间线、质量状态和证据侧栏。先保证每个状态能解释、每个数字有来源，再做动效和外观润色。

## 开发批次按验收衔接

| 批次 | 开发范围 | 交付验收 | 依赖与边界 |
| --- | --- | --- | --- |
| B1：工作台只读数据契约 | 先定义 revision、lineage、版本 Diff、评测任务列表与详情的 DTO；实现明确启用的只读管理 API 和契约测试 | 对本次验收库返回真实的 passed → failed → passed 历史；每个任务能定位触发 revision；分页、未知 ID、权限拒绝有明确结果 | 沿用本机默认与鉴权；不扩大 U18 上下文端点职责，不新增写接口 |
| B2：V3 生命周期与变更视图 | 在现有页面接入 API adapter，增加变更时间线、任务详情和证据导航 | 不依赖固定黄金截图，真实任务结果能从后端出现在页面；失败详情可跳转到对应历史版本与原文 | 依赖 B1；Snapshot V1 保持兼容，静态 fixture 与 live 数据明确区分 |
| B3：V4 评测视图与导览 | 增加指标和检查项展示、可比结果对照、无答案与过期知识解释，以及演示导览 | 演示者在隔离库用 CLI 更新文档，页面刷新或轮询看到新任务；能讲清正常、故障和修复的完整故事 | 依赖 B2；对比前检查评测集、策略、检索参数及时间口径，不把不同配置连成一条“改善趋势” |
| B4：受控变更交互 | 另行设计知识更新、候选批准与时效操作的命令接口；先在演示副本开放限定操作 | 浏览器完成一项允许的变更，服务端留下审计并触发评测；重复点击、无权限与评测失败均不误报 | 依赖只读展示稳定；必须具备真实身份/权限、来源校验、输入限制、幂等与操作确认；浏览器不提交任意路径或数据库凭证 |
| B5：U22 MCP 与对外展示准备 | 在稳定查询服务上实现只读 search/get/context MCP，并完成客户端验收；随后安排演示打包与发布审核 | Agent 查询与工作台能核对同一知识版本、证据和引用；演示可重置，公开数据通过检查 | MCP 不阻塞 B1～B3；只有用户明确授权后才创建发布、正式部署或处理生产数据 |

每个批次作为独立开发切片，在当前 feature 分支完成测试并推送；不要求每批立即合并 main。进入下一批前检查验收场景、数据契约和剩余风险。涉及公开发布时，另行确认 PR、合并、tag、包发布和部署，不能把开发完成视为发布授权。

## 下一批先做 B1

先补前端真正需要的只读接口及其契约测试，不先扩展 MCP，也不一次性增加全部后台管理功能。最小链路是任务列表、任务详情、触发 revision、版本 Diff 与来源证据。

任务详情应保留当时的知识指纹、评测集版本与策略。页面展示历史报告时，不能用最新正文替代当时的引用；缺少历史证据则明确标记不可用。状态更新需要 loading、空列表、运行失败、blocked 和 superseded 等处理，不能只设计绿色通过状态。

## 展示安全与后续能力

自动评测内部报告当前不保存 query 或源全文。B1 不应为了演示直接暴露 SQLite 表、私密评测集或绝对路径。需要用例级失败诊断时，作为单独的、可授权读取的接口设计，返回必要的用例标识、预期 lineage 与证据定位，不默认导出原始问题。

当前同步评测会增加变更耗时。首个现场演示继续使用单库、小规模评测，不把它包装成异步生产服务。后台调度、真实 embedding provider、向量/混合自动评测和 Agent 答案质量评测放在可演示链路稳定之后，再分别补 provider 配置、隐私边界、成本与验收数据。

外部演示默认使用可公开的项目文档和独立副本；用户业务库只用于经授权的私密验收。公开部署前还需确认认证、数据脱敏、运行可恢复性和服务暴露边界。
